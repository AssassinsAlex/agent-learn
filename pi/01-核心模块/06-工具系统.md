# 工具加载、执行与结果

源码入口：[agent-loop.ts](https://github.com/earendil-works/pi/blob/864b35c462f9623579b068e9cab848419f9e1d0f/packages/agent/src/agent-loop.ts)、[types.ts](https://github.com/earendil-works/pi/blob/864b35c462f9623579b068e9cab848419f9e1d0f/packages/agent/src/types.ts)、[agent-harness.ts](https://github.com/earendil-works/pi/blob/864b35c462f9623579b068e9cab848419f9e1d0f/packages/agent/src/harness/agent-harness.ts)。

内置工具专题：[核心 Tools 与 Web Search 边界](13-核心Tools与WebSearch边界.md)。

## 1. 加载与执行的边界

```text
coding-agent
  内置工具 + SDK 工具 + 扩展工具
    -> _refreshToolRegistry()
    -> _toolRegistry: Map<name, AgentTool>
    -> setActiveToolsByName()
    -> agent.state.tools / Harness activeTools
    -> AgentContext.tools
    -> provider 收到工具 schema
    -> 模型返回 toolCall
    -> agentLoop.executeToolCalls()
```

agent-core Harness 不扫描插件、不发现文件、不创建 coding tool。构造 `AgentHarness` 时调用方直接传入 `tools`；Harness 只校验名称、保存工具，并依据 `activeToolNames` 生成本回合的 `activeTools`。真正的工具发现和装配是 coding-agent 的职责。

## 2. 工具契约

`AgentTool` 包含 `name`、`description`、参数 schema、`label` 和 `execute(toolCallId, params, signal, onUpdate)`。可选的 `prepareArguments` 在 schema 校验前规范化参数，`executionMode` 可要求顺序执行。

`AgentToolResult` 的主要字段：

```ts
{
  content: TextContent[] | ImageContent[],
  details: unknown,
  usage?: Usage,
  addedToolNames?: string[],
  terminate?: boolean
}
```

`content` 给模型看；`details` 给 UI/日志/扩展使用；`usage` 是工具自身用量，不参加主 LLM context accounting；`terminate` 是停止当前工具批次的提示，只有批次内所有结果都为 true 才停止。工具失败应抛异常，runtime 会统一转换成错误结果。

## 3. Coding-agent 的 load 流程

`AgentSession._refreshToolRegistry()` 会合并内置定义、扩展 runner 工具和 SDK custom tools，应用 allow/exclude 过滤，用 `wrapRegisteredTools()` 统一包装，建立 `_toolRegistry`，再计算 active names。`setActiveToolsByName()` 从 registry 取实际对象，写入 `agent.state.tools`，并重建 system prompt 的工具说明。

这是“工具对象进入运行时”的过程；模型收到的是名称、描述和 JSON schema，不是 `execute()` 函数，因此模型只能提出调用，不能直接执行本地代码。

## 4. 一次 tool call 的执行链

```text
assistant.content
  -> 筛选 type = toolCall
  -> 选择 sequential / parallel
  -> tool_execution_start
  -> 查找工具
  -> prepareArguments（可选）
  -> validateToolArguments(schema)
  -> Harness beforeToolCall hook
  -> tool.execute(validatedArgs, signal, onUpdate)
  -> Harness afterToolCall hook
  -> tool_execution_end
  -> 创建 ToolResultMessage
  -> message_start + message_end
  -> turn_end
  -> 下一次 provider 请求
```

具体规则：

- 找不到工具、参数校验失败、abort 或 `beforeToolCall` block，都不执行工具，生成 `isError: true` 的 immediate result。
- `execute()` 抛异常也被捕获，转为文本错误结果，loop 仍可把错误交给模型恢复。
- assistant 输出因达到 token limit 而截断时，所有 tool call 都不执行，统一要求模型重新发起完整参数。
- 默认并行；但全局 `toolExecution: "sequential"` 或任一工具声明 `executionMode: "sequential"` 时整批顺序执行。
- 并行时预检按顺序完成，实际执行并发；`tool_execution_end` 按完成顺序发出，但最终 tool-result message 按 assistant 原始调用顺序排列。

## 5. 工具结果的三层表现

### 流式更新

`execute()` 可调用 `onUpdate(partialResult)`，runtime 发出 `tool_execution_update`，供 UI 显示进度。工具 Promise 结束后的迟到 update 会被忽略；partial update 不单独写入模型上下文。

### 最终执行事件

工具结束后发出 `tool_execution_end`，其中结果已经经过 `afterToolCall` 的覆盖逻辑。Harness 将 `beforeToolCall` 映射为 `tool_call` hook，将 `afterToolCall` 映射为 `tool_result` hook，可审批、阻止、脱敏、替换 content/details、重标记错误或设置 terminate。

### 模型可见消息

runtime 用 `createToolResultMessage()` 生成：

```ts
{
  role: "toolResult",
  toolCallId,
  toolName,
  content,
  details,
  usage,
  addedToolNames?,
  isError,
  timestamp
}
```

它通过 `message_start/message_end` 进入 `AgentContext`；Harness 在 `message_end` 时调用 `session.appendMessage()` 持久化。下一次 provider 请求由 `convertToLlm()` 把它转换为标准工具结果消息，模型才真正看到结果。

```text
assistant(toolCall)
  -> ToolResultMessage（context + session tree）
  -> turn_end / prepareNextTurn
  -> streamAssistantResponse()
  -> provider 消费 tool result
```

## 6. Pi 对工具结果的后处理

答案是“有多层后处理”，但没有一个通用的 LLM 二次总结步骤：

### 第一层：具体工具自己的处理

例如 `bash` 工具在返回 `AgentToolResult` 前会合并 stdout/stderr、清理输出、按字节上限截断，并在有完整输出文件时附带 `fullOutputPath`。这属于工具实现层，因为只有工具自己知道输出如何安全展示。其他工具也可能在 `execute()` 内做图片缩放、路径格式化或权限错误转换。

### 第二层：runtime 的统一收尾

`agent-loop.ts/finalizeExecutedToolCall()` 会：

1. 接收 `execute()` 的最终结果；
2. 调用 `afterToolCall`；
3. 用 hook 返回值覆盖 `content`、`details`、`usage`、`isError`、`terminate`；
4. 如果 hook 自己抛错，把整个结果替换为错误结果；
5. `createToolResultMessage()` 将结果规范化为 `role: "toolResult"`，缺失 content 时补成空数组，并带上 `toolCallId/toolName/isError`。

这一步不是摘要，而是确定“最终哪一份结果”进入事件流和模型上下文。

### 第三层：coding-agent / Extension 后处理

coding-agent 将 runtime 的 `afterToolCall` 连接到扩展的 `tool_result` 事件。扩展可以根据工具名和参数：

- 替换或脱敏模型可见的 `content`；
- 修改 `details` 供 UI 使用；
- 重标记 `isError`；
- 修改 `usage`。

因此扩展 hook 返回的内容会覆盖原始工具结果，并同时影响 `tool_execution_end` 和后续 `ToolResultMessage`。它不是旁路日志，而是结果的正式修改点。

### 第四层：Session 与 Compaction 的投影

最终 `ToolResultMessage` 在 Harness 的 `message_end` 阶段写入 Session。之后如果发生 compaction，摘要 prompt 会再对工具结果做一次“仅用于摘要请求”的截断（当前单个结果最多 2000 字符）。这不会改写 Session 中保存的原始结果，也不会改写 retained tail。

```text
原始执行输出
  -> 工具自身清理/截断
  -> afterToolCall / extension 覆盖
  -> ToolResultMessage 规范化
  -> Session 持久化
  -> 下一轮模型直接消费
  -> compaction 时另做摘要序列化截断
```

所以要区分：**执行结果后处理**会改变模型即将看到的正式结果；**compaction 截断**只改变摘要模型看到的副本。

## 7. 与 Session 和 Compaction 的关系

工具结果是普通 `AgentMessage`，以 `role: "toolResult"` 保存到 session tree。compaction 时工具调用会序列化工具名和 JSON 参数，工具结果参与 token 估算；摘要 prompt 中单个工具结果最多保留 2000 字符，而 retained tail 仍保留原始完整消息。因此摘要中的工具文本与 session 原文是两种不同投影。

## 8. 最终边界地图

```text
加载 registry：coding-agent / application
工具 schema：provider 可见
工具执行：agent-loop runtime
执行审批/结果修补：Harness hooks
文件、shell 等副作用：具体 AgentTool + ExecutionEnv
持久化：Harness -> Session
下一轮消费：ToolResultMessage -> convertToLlm -> provider
```

最容易混淆的是：模型选择工具不等于工具被加载；工具执行完成也不等于模型已经看到结果，必须生成最终 `toolResult` 并启动下一次模型请求。
