# Pi 全项目学习覆盖审查

## 审查结论

当前学习已经扎实覆盖了 `packages/agent` 的通用运行时：agent loop、Harness、树状会话、上下文投影、compaction、工具调用与 prompt 包装。这足以解释一个通用 agent 如何运行。

但它还不能完整解释 **Pi CLI 为什么能作为一个可配置、可扩展、可恢复且可嵌入的 coding agent 工作**。最高价值的下一层是：

1. `coding-agent` 的实际运行时装配：`AgentSessionRuntime`、`AgentSessionServices`、`AgentSession`；
2. `pi-ai` 的模型协议适配与认证链；
3. extension + project trust 的产品扩展与安全边界。

换句话说，已学的是通用 agent 的“发动机”；待学的是 Pi 如何供油、选路、加载附件并把发动机接到真实终端上。

## Pi 的整体装配关系

```text
CLI / stdin
  -> coding-agent main.ts（解析参数，选择 interactive / print / json / rpc）
  -> AgentSessionRuntime（可替换的运行时宿主）
  -> AgentSessionServices（一次性装配 settings、models、auth、resources、extensions）
  -> AgentSession（Pi CLI 的策略层：持久化、自动压缩、overflow 恢复、事件）
  -> pi-agent-core Agent / agentLoop / Harness（通用执行内核）
  -> pi-ai Model.stream（按 provider 协议发请求并归一化流）
  -> tools / extensions / TUI 或 RPC（副作用与可观察输出）
```

此图表达的是**持有和调用关系**，不是 TypeScript 继承。特别要保持三个对象的边界：

| 对象 | 所在包 | 角色 |
| --- | --- | --- |
| 通用 `Session` / `AgentHarness` | `agent` | 可复用的会话与 agent 编排能力。 |
| `SessionManager` | `coding-agent` | Pi CLI 的 JSONL 会话日志、树、版本迁移及当前 branch projection。 |
| `AgentSession` | `coding-agent` | 对用户界面暴露的长期 session controller；将持久化、extension、自动压缩与 Agent 事件接合。 |

## 高价值遗漏设计

### P0：真实运行时与自动策略

学习入口：[agent-session-runtime.ts](https://github.com/earendil-works/pi/blob/864b35c462f9623579b068e9cab848419f9e1d0f/packages/coding-agent/src/core/agent-session-runtime.ts)、[agent-session-services.ts](https://github.com/earendil-works/pi/blob/864b35c462f9623579b068e9cab848419f9e1d0f/packages/coding-agent/src/core/agent-session-services.ts)、[agent-session.ts](https://github.com/earendil-works/pi/blob/864b35c462f9623579b068e9cab848419f9e1d0f/packages/coding-agent/src/core/agent-session.ts)。

要回答：启动时哪些共享服务只创建一次；新建、切换、导入 session 时哪些对象替换；`AgentSession` 怎样监听 core Agent 事件写入 JSONL；threshold compaction 与 context-overflow compaction 的触发、取消、至多一次重试及队列衔接如何工作。

这也是对现有 compaction 笔记最值得补的一层：已学习“如何压缩 context”，尚未完整学习“CLI 在何时自动压缩并如何恢复失败请求”。

### P0：`pi-ai` 的 provider 归一化

学习入口：[types.ts](https://github.com/earendil-works/pi/blob/864b35c462f9623579b068e9cab848419f9e1d0f/packages/ai/src/types.ts)、[pi-messages.ts](https://github.com/earendil-works/pi/blob/864b35c462f9623579b068e9cab848419f9e1d0f/packages/ai/src/api/pi-messages.ts)、[transform-messages.ts](https://github.com/earendil-works/pi/blob/864b35c462f9623579b068e9cab848419f9e1d0f/packages/ai/src/api/transform-messages.ts)。

Pi 没有让 agent loop 直接面对 Anthropic、OpenAI Responses、Google 等不同事件和 message 约束；它定义统一 `Model`、`Context`、`Message`、`AssistantMessageEvent` 和 `StreamFunction`。每个 API adapter 负责请求/响应转换，最后把流收敛成 agent-core 消费的事件。

应专门拆解四件事：provider API 如何改写消息；tool schema 如何适配；`supportsToolSearch` 的 deferred schema lookup 为什么不是网络搜索；认证、retry、缓存和 context overflow 如何在 API 边界表达。

### P0：扩展与项目信任

学习入口：[loader.ts](https://github.com/earendil-works/pi/blob/864b35c462f9623579b068e9cab848419f9e1d0f/packages/coding-agent/src/core/extensions/loader.ts)、[runner.ts](https://github.com/earendil-works/pi/blob/864b35c462f9623579b068e9cab848419f9e1d0f/packages/coding-agent/src/core/extensions/runner.ts)、[project-trust.ts](https://github.com/earendil-works/pi/blob/864b35c462f9623579b068e9cab848419f9e1d0f/packages/coding-agent/src/core/project-trust.ts)。

Pi 的扩展不是简单“加一个 tool”：它可注册命令、工具、provider、事件 handler、会话操作和部分 UI。项目下 `.pi` 资源、`.agents/skills` 与可安装 package 都可能触发第三方代码执行，所以 Pi 将是否加载这些项目资源放在 project-trust 决策之后；无 UI 模式在未明确可信时默认不信任。

安全学习时要明确边界：trust 保护的是**项目资源加载**，不是给内置 `bash`、`read` 等工具实现通用沙箱。已信任扩展或 tool 本身仍应视为有宿主进程权限的代码。

### P1：模型选择、配置与凭据生命周期

学习入口：[model-runtime.ts](https://github.com/earendil-works/pi/blob/864b35c462f9623579b068e9cab848419f9e1d0f/packages/coding-agent/src/core/model-runtime.ts)、[provider-composer.ts](https://github.com/earendil-works/pi/blob/864b35c462f9623579b068e9cab848419f9e1d0f/packages/coding-agent/src/core/provider-composer.ts)、[runtime-credentials.ts](https://github.com/earendil-works/pi/blob/864b35c462f9623579b068e9cab848419f9e1d0f/packages/coding-agent/src/core/runtime-credentials.ts)。

这里要建立一条端到端数据线：settings 的 user/project scope 与 CLI override -> `ModelRegistry` / `ModelResolver` -> `ProviderComposer` 的 URL、header、compatibility 组合 -> API key/OAuth token 解析 -> `pi-ai` provider stream。它决定了多模型和自定义兼容 API 的行为，不是 UI 设置的附属细节。

### P1：会话日志与恢复，不只是一棵树

学习入口：[session-manager.ts](https://github.com/earendil-works/pi/blob/864b35c462f9623579b068e9cab848419f9e1d0f/packages/coding-agent/src/core/session-manager.ts)。

此前所学树状 Session 很重要，但 CLI 还有自己的 JSONL `SessionEntry` 联合：message、model/thinking change、compaction、branch summary、custom entry/message、label、session info。它还维护 session 文件 header、`parentSession`（跨文件 fork）及 v1-v3 migration。应重点比较：同文件的 `parentId` 分支与跨文件 `parentSession` fork 分别解决什么问题；哪些 entry 会进 LLM context，哪些只为 UI/扩展恢复状态而存。

### P1：控制面与可观察性

学习入口：[rpc-mode.ts](https://github.com/earendil-works/pi/blob/864b35c462f9623579b068e9cab848419f9e1d0f/packages/coding-agent/src/modes/rpc/rpc-mode.ts)、[telemetry.ts](https://github.com/earendil-works/pi/blob/864b35c462f9623579b068e9cab848419f9e1d0f/packages/coding-agent/src/core/telemetry.ts)、[timings.ts](https://github.com/earendil-works/pi/blob/864b35c462f9623579b068e9cab848419f9e1d0f/packages/coding-agent/src/core/timings.ts)。

interactive、print、JSON、RPC 不只是展示皮肤。`rpc` 模式用 JSONL 接收 command、输出 session event/response，并把 extension UI 请求转换为宿主可响应的协议；这是嵌入其他应用的清晰边界。随后再看 TUI 的组件/终端差分绘制，能避免把终端渲染误当成 agent 的状态源。

### 重要边界：长期经验不是 Pi 的默认闭环

Pi 默认会持久化 session 日志，也可加载可复用的 Skills、`AGENTS.md`/`CLAUDE.md` 上下文文件、prompt template 和 extension；这些都是**未来任务可见的长期知识载体**。但在此提交中没有发现默认实现会自动执行“轨迹/结果 -> 反思或抽取 -> 写入经验库 -> 检索相关经验 -> 注入后续上下文”的 pipeline。

不要被 `packages/agent/src/harness/session/memory-repo.ts` 与 `memory-storage.ts` 误导：这里的 memory 是 `InMemorySessionRepo` / `InMemorySessionStorage`，即进程内测试或临时会话后端，并非语义记忆库，也不会跨进程保留经验。

这恰好是算法工作者最值得扩展的空位。一个严谨的 extension 方案应把以下对象分离：

```text
任务轨迹（session / tool result / outcome）
  -> 经验候选抽取（成功策略、失败模式、约束）
  -> 验证与去重（来源、适用条件、版本、置信度）
  -> 持久经验库（结构化字段 + 向量/关键词索引）
  -> task-conditioned retrieval（预算和重排）
  -> system/context 注入，并记录实际收益
```

不能把 compaction summary 当长期经验：它的目标是为**当前 branch**压缩上下文，内容可能带有任务偶然细节，且没有跨任务检索、质量门控或效果归因。

## 审查后的学习边界

Pi 目前没有内置互联网 web-search 工具；`grep`/`find` 是工作区检索，`supportsToolSearch` 是部分 provider 的延迟 tool-schema 查找。联网检索应经 `bash`、extension 或 MCP/自定义 tool 引入，并自行处理来源、内容预算与 prompt-injection 风险。详见[核心 Tools 与 Web Search 边界](../01-核心模块/13-核心Tools与WebSearch边界.md)。

本轮审查不把每个 provider、TUI 组件或 server handler 逐文件抄录为学习目标。它们应由上述端到端问题驱动，否则会失去 agent 系统的主线。
