# 上下文管理

## 1. 上下文组装公式

一次请求可以抽象为：

```text
LLM request
  = canonical request header
  + rendered system prompt
  + tool schemas
  + session.deriveMessages()
  + current claimed/injected messages
```

其中 system prompt 和 tools 在 `systemPrompt.assemble()` 中生成，Session history 则从当前 surface 派生。

## 2. `agent.inject()` 的语义

`inject()` 把消息放进 Agent 的 `next-step` inbox，但不主动唤醒 Agent。它适合预置运行时上下文：上下文先等待，下一条真正唤醒 Agent 的输入到达后再被模型看到。

这与 `steer()` 不同：`steer()` 会唤醒当前 Agent，并要求当前 turn 尽快进入下一 step。

## 3. 为什么要求“模型可见即已记录”

如果某个插件直接修改内存 request，resume、fork、UI 回放和 telemetry 就无法重建同一输入。因此架构文档规定：新的模型可见输入必须通过 Session Event Log 表达。

`agent/request` 可以改 frozen call configuration，但不能偷偷改 messages；消息必须走 logged channels。

## 4. Pressure measurement

`ctx.tokenMeter.measure(session)` 以最新 durable request envelope 和当前 surface 为基础，估算：

```text
system + tools + envelope + message surface + assistant/tool 内容
```

它是统一的 pressure authority；模型上下文窗口则由具体 adapter 的 model info 提供。

### 4.1 它不是每次从日志全量重算

`TokenMeter` 为每个 Session 维护一个 replay fold：从上次消费的 `consumedEvents` 继续处理新事件，并缓存当前 surface 中每个 message node 的启发式 token 值及 `surfaceTokens` 总量。

```text
新增 surface event
  -> estimate 新 message
  -> append 一个 priced node
  -> surfaceTokens += 新值

surface replacement
  -> 计算被 shadow 节点的 token 总和
  -> 写入 replacement token
  -> surfaceTokens += replacement - removed
```

因此日志 replay 和 token 累加是增量的；但 `measure()` 会复制整个当前 surface，返回独立、不可变的 node 快照，所以一次 measurement 的快照构造成本是 `O(surface)`。它缓存的是当前 surface 的 message-level price，不是逐个 content block 的长期 token 表。

### 4.2 估算公式与 provider usage

默认估算器不是 provider tokenizer，而是固定启发式：文本约按 4 个字符一个 token，再加结构开销。message 价格为：

```text
estimateMessage(message) = estimateContent(content) + 4
```

文本/reasoning block：`ceil(text.length / 4) + 4`；tool-call 会分别估算名称和 arguments；tool-result 递归估算内部 content；system 和 tools 也单独估算。

成功的 assistant 请求可以建立 provider usage anchor。只有当前 canonical request envelope 与该请求相同，且 provider usage 不小于该次完整启发式价格时，才复用 provider usage；否则回退为当前 envelope + 当前 surface 的启发式估算。压缩 replacement 通过带符号 delta 立即降低当前 surface 价格。

## 5. 上下文变化的两条路径

```text
新增输入/工具结果
  -> append surface node

压缩/裁剪
  -> append replacement node
  -> shadow old surface node
```

日志不会丢失旧事件，下一次 `deriveMessages()` 只使用新的 surface。

## 6. 压缩在上下文管理中的位置

压缩不是直接修改 `deriveMessages()` 的临时过滤器，而是先在 Session 日志中追加 `compaction/*` 和 replacement，再由同一套 surface 派生逻辑生成后续请求。正常步骤边界由 `agent/pre-step` 检查压力；provider 确认 overflow 则由 `agent/request-error` 触发恢复。详细流程见[Compaction 全景](04-Compaction全景.md)。
